# 闸门③ 拦下的真错位 —— 诊断与修法（2026-10-04 20:20）

## 一、被拦下的事实

上传完成后核验，`cloud_run384.sh` 的清册同序闸门给出：

```
[chk] 类清单一致: True | 类数: 750 750
[chk] 清册同序: 5/750 类顺序完全一致 | 不同序: ['0000','0001',...]
[chk] 文件位置一致: 92907/148695 = 62.48%
⇒ 约 37.5% 的图像在 manifest 里的行号发生了变化
```

★ **闸门③ 是对的，它拦下了一个真的静默错误。** 若直接点火，低相似掩码会有
**37.5% 指错行**，而代码里的断言**只校验张数、不校验行序**，不会报错。

---

## 二、根因（三层，逐层查证）

### 层 1：manifest 的行序不是字典序
`src/data.py:184-199`：
```python
dirs = list_class_dirs(root)        # 类目录：sorted ✅
for f in d.iterdir():               # ★ 类内文件：裸 iterdir（不排序！）
    rows.append((str(f), d.name, int(cid)))
```
⇒ 行序 = **`Path.iterdir()` 原始顺序**（等价 `os.listdir`）= **文件系统的 inode 排列顺序**。

### 层 2：两套缓存的 inode 顺序天然不同
| 缓存 | 生成方式 | inode 顺序来自 |
|---|---|---|
| `_preproc`（320） | 云端原地 `build_preproc_cache.py` 顺序写 | **源训练目录**的顺序 |
| `_preproc384` | 我**从本地 tar 传上去** | **tar 流内顺序** = 本地 `find`（字典序） |

★ **决定性证据**：两套缓存**排序后完全一致**（实测 `sorted()` 前 5 项逐字相同），
差异**纯粹**来自 `listdir` 的原始返回序。⇒ 这是**传输方式引入的**，不是数据本身不同。

### 层 3：`feat_train.npy` 的行序被"钉"在了 320 那份上
`src/config.py:49-52` —— ★★ 关键：
```python
OUT_DIR   = ROOT / "outputs"         # ← 跟随 AIC_ROOT
CACHE_DIR = OUT_DIR / "cache"        # ← 所以 feat_train.npy **不随 AIC_DATA_DIR 切换**
```
而 `cloud_run384.sh` 只切了 `AIC_DATA_DIR`（造 `data384/` 工作区）。

⇒ 跑 `data384/` 时：
- manifest 行序 = **384 缓存的 iterdir 顺序**
- `feat_train.npy` 行序 = **320 缓存的 iterdir 顺序**（旧文件，未重建）
- ⇒ **两者错位 37.5%**

### 消费点（错位会被谁吃掉）
`src/finetune_lora.py:1170-1171`：
```python
Xf = np.load(C.CACHE_DIR / "feat_train.npy")   # 320 的行序
va_idx = np.where(val_mask)[0]                 # 384 的行号
low, ms = CLF.low_sim_mask(Xf, labels, va_idx, np.arange(len(labels))[~val_mask])
```
唯一守卫（`finetune_lora.py:1173-1176`）：
```python
if len(low) != len(va_labels):   # ★ 只比长度！行序错了照样过
    raise SystemExit(...)
```

## 三、三条修法对比

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A · 重建 feat_train** | 在 384 缓存上重跑 `extract --rebuild` | 需 GPU 前向 148,695 张（~20min）+ 磁盘 300M | ★ **低相似子集张数会变**（`cloud_run384.sh:41-43` 已明写：会让子集张数变 ⇒ **与历史各组失去横比资格**） |
| **B · manifest 强制排序** | `for f in sorted(d.iterdir())` | 零成本 | ★★ **会平移全历史行序**：所有旧 `feat_train.npy` / `probs_val_*.npy` / 掩码口径全部失效 ⇒ **比 A 危险得多** |
| **C · 让 384 缓存的 iterdir 顺序 == 320** | 在云端按 320 的 `listdir` 顺序**重建** 384 目录（重命名/硬链接） | 零 GPU，几分钟 | ★ 低。**唯一要做的就是把 inode 顺序摆回去** |

---

## 四、我的选择：**方案 C**（前提已实测验证）

理由：
1. **不改任何源码** ⇒ 不动 `feat_train.npy` 的行序 ⇒ 历史全部可比；
2. **零 GPU 成本** ⇒ 不烧钱；
3. **直击根因** ⇒ 错位的唯一来源就是"384 目录的 inode 顺序和 320 不同"，
   把它摆成一致，问题**从源头消失**，而不是靠断言去"容忍"。

### ★ 前提已实测验证（这一步不能省）
在云端实跑：源目录用 `mmm aaa zzz bbb yyy` 的顺序创建，再**按 `zzz aaa mmm bbb yyy`
的顺序硬链接**，结果目标目录的 `listdir` 返回 **`zzz aaa mmm bbb yyy`**
⇒ **`listdir` 返回的就是创建顺序**，方案 C 成立。

（踩坑记录：第一次用 `ls` 看结果，`ls` 会**排序输出**，看起来"怎么链都是字典序"，
差点误判方案 C 不成立。**必须用 `os.listdir()` 读，不能用 `ls`。**）

### 具体做法
在云端建**新目录** `data/_preproc384s/train`（**不动已传好的 `_preproc384`，保底**），
按 **320 缓存的 `listdir` 顺序**逐类逐文件**硬链接**过去。硬链接：
- **不占额外磁盘**（inode 复用，实测同一 inode、`st_nlink=2`）
- `iterdir()` 顺序 = **创建顺序**（已实测）⇒ 按 320 的顺序创建即得同序
- 若硬链接失败（跨设备）⇒ 自动退化为 `copy2`（占 11G，磁盘余 11G 勉强够）

脚本：`scripts/rebuild_384_order.py`（`--build` / `--verify`），自带四道自证：
① 逐类逐文件同序（目标 **750/750**）；② `st_nlink≥2` 证明真硬链接；
③ 分辨率抽查仍 PASS；④ 磁盘增量 ≈0。

★ **判据：重建后重跑闸门③ 必须 750/750，否则拒绝点火。**

## 五、附带发现（同样重要）

**闸门③ 的判据本身写错了对象。**
`cloud_run384.sh:131` 用的是**裸 `listdir` 比序**：
```python
if la != lb:  diff.append(c)
```
但真正决定 manifest 行序的**就是** `iterdir` 顺序 —— 所以判据是**对的**。
我起初误以为"排序后一致就没事"，**是错的**：训练代码用的是 `iterdir`，
不是 `sorted(iterdir)`。⇒ **闸门③ 不该放宽，反而该保留并强调。**

## 附：本次核查命令（可复算）

```bash
# 量化错位
/root/miniconda3/bin/python -c "
import os
A='/root/autodl-tmp/aic/data/_preproc/train'
B='/root/autodl-tmp/aic/data/_preproc384/train'
cls=sorted(os.listdir(A)); tot=same=0
for c in cls:
    la=os.listdir(os.path.join(A,c)); lb=os.listdir(os.path.join(B,c))
    tot+=len(la); same+=sum(1 for x,y in zip(la,lb) if x==y)
print('位置一致率 %.2f%%' % (100*same/tot))"
```
