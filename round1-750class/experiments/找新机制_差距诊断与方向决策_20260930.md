## 三、★ 三个我认为最该做的（按可执行性）

### 3.1 池化轴（**立刻可跑，代码已就绪**）

**为什么它是第一**：

- 全项目走 `get_image_features` ⇒ **只取 CLS token**
- 448 输入 ⇒ 196 个 patch token **被整块丢弃**
- 低置信区的 1135 个错分，本质是"模型没看到区分性细节"
  ⇒ 而 patch token 里**恰恰装着这些细节**

**已就绪的东西**：
- `--pool {cls,gem,mean,attn}` ＋ `--pool-multi` 已实现
- 448 下实测确得 `(1,197,768)` ✓（**参数生效已自证**）
- `probe_bucket_recheck.py` 的 `build_model_from_ckpt` 已能正确恢复池化配置
  ⇒ 出包链路不会静默丢权重（这是 Adapter 事故后加的守卫）

**建议第一跑**：`--pool mean`（最简单、无学习参数、直接检验"CLS 是否丢了信息"）
**建议第二跑**：`--pool multi`（cls+mean+gem 拼接）

⚠️ **注意**：`--pool gem` 单独跑已关闭（无增益）。但**当时没看低置信区分桶读数** ——
很可能 gem 在高置信区无增益、在低置信区有增益，被整体 acc 掩盖了。
⇒ **重跑时应记录分桶读数，不只记整体 acc。**

### 3.2 互吞对的推理侧专治（**需写码，但成本极低**）

已知 90 对互吞类（`0270↔0612` 等），覆盖 **16.5% 的错分**。

**做法**：在推理侧，对预测落在"互吞对"内的样本，用**更高分辨率的视图**重判
（因为这些对的区分判据在细节上）。这是**纯推理侧改动，零训练成本**。

⚠️ **合规红线**：互吞对名单**必须从训练集/留出集统计得到，绝不能从测试集**。
（测试集特征不得参与任何决策 —— 铁律，违者取消资格。）

### 3.3 多尺度融合的**置信度自适应**（**需写码，纯推理**）

现在 15 视图是 **`power` 平均 t=4**（等权）。但：
- 高置信样本：多视图**一致**，平均无害
- 低置信样本：多视图**分歧**，等权平均会**抹平**那个可能正确的信号

**做法**：按**视图间一致性**加权 —— 一致性高就多信，分歧大就少信。
这在 `[0.20,0.80)` 区间可能有效，且**零训练成本**。

### 4.2 ★★ 一个必须记住的性能坑（已修）

**症状**：空载烟测（750 张）**82 秒**；全量（7537 张）**与训练并存**时，
**11 分钟连第一个臂都没跑完**，日志停在加载模型后不动。

**根因**：**推理脚本没设 `OMP_NUM_THREADS`** ⇒ torch 按 `nproc`（**128**）起线程，
与训练侧的 **8 个 dataloader worker + 主进程**抢 CPU
⇒ 推理脚本的 128 线程被反复抢占，单步极慢。

**误判路径**（值得记）：先怀疑死锁 ⇒ `/proc/<pid>/status` 显示
`State: R (running)`、`Threads: 132`、CPU TIME **2h04m** ⇒ **是在算，不是卡死**；
再怀疑 CPU 超订 ⇒ load 9.21 / 128 核 ⇒ 也不是。最后才定位到线程数。

**修法（两处都要）**：
```python
os.environ.setdefault("OMP_NUM_THREADS", "8")   # 必须在 import torch 之前
os.environ.setdefault("MKL_NUM_THREADS", "8")
torch.set_num_threads(8)                        # 运行时兜底
```

**修复效果实测**：全量 7537 张 **>11 分钟 → 86 秒**（与空载烟测 82s 一致）。

⚠️ **连带踩到的 SSH 坑**：`pkill -f probe_conf_bucket` **自匹配了承载它的 SSH 会话**
⇒ **SSH 直接 rc=255 断开，后续命令从未执行**。
⇒ 必须用括号形式 `pkill -f '[p]robe_conf_bucket'`，或
`ps -eo pid,cmd|awk '/pat/ && !/awk/{print $1}'` 再点名 `kill`。
