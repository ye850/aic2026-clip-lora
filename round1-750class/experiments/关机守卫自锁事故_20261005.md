# 关机守卫自锁事故 —— 复盘与修复（2026-10-05 00:2x）

> 触发：10-04 23:5x 用户问"需不需要我手动关机"。查下去发现
> **守卫脚本有一个确定性 bug：它永远不会关机。** 机器已空转 3.5 小时。

---

## 〇、一句话

> `chainZ3_shutdown.sh` 的**锁名单里包含它自己的名字**，
> 而它启动时又把自己的 PID 写进那个锁 ⇒ **判据每次都找到"自己活着"**
> ⇒ 永远判"忙" ⇒ **永不关机**。
> ⇒ 空转 3.5h（20:21→23:5x），按 ¥2.18/h 计 **白烧约 ¥7.6**，最后靠**用户手动关机**。

---

## 一、事故链条（每一环都有证据）

### 1.1 机器状态：GPU 早已空

| 时间 | GPU 进程 | 名单进程 | 守卫判读 |
|---|---|---|---|
| 20:21 | 1 | 9 | 忙 |
| 22:21 | **0** | **1** | 忙 ← 从这里起**已无任何任务** |
| 22:51 | 0 | **0** | 忙 |
| 23:21 | 0 | 0 | 忙 |
| 23:51 | 0 | 0 | 忙（已等 210min） |

⇒ 从 **22:21** 起 `GPU进程=0 名单进程=0`，**唯一"活"的就是那个"活锁=1"**。

### 1.2 那个"活锁"是谁？——**是守卫自己**

```
$ cat outputs/.chainz3.lock
5785
$ ps -o pid,cmd -p 5785
   PID CMD
  5785 bash chainZ3_shutdown.sh        ← 就是守卫本身
```

### 1.3 根因：三行代码的合成错误

`chainZ3_shutdown.sh`：

```bash
第 39 行  LOCK=$RR/outputs/.chainz3.lock                  # 自己的锁
第 40 行  LOCKS="chainaa … chaino chainz3 r448real"        # ★ 名单里含 chainz3
第 54 行  echo $$ > "$LOCK"                               # 把自己的 PID 写进去

主循环：
          for l in $LOCKS; do
            p=$(cat "$RR/outputs/.${l}.lock" 2>/dev/null || echo -)
            if [ "$p" != "-" ] && kill -0 "$p" 2>/dev/null; then ALIVE=$((ALIVE+1)); fi
          done
          # ⇒ 当 l=chainz3 时，读到的是自己的 PID，kill -0 必然成功
          # ⇒ ALIVE 恒 ≥ 1 ⇒ 恒判"忙" ⇒ 安静计数永远归零
```

### 1.4 对比证据（同族脚本一对一比，排除"环境问题"）

| 脚本 | 自己的锁名 | `LOCKS` 名单 | 能否关机 |
|---|---|---|---|
| `chainZ2_shutdown.sh` | `.chainz2.lock` | `chainp2 … chaino` → **不含 chainz2** | ✅ 正常 |
| **`chainZ3_shutdown.sh`** | `.chainz3.lock` | `… chaino **chainz3** r448real` | ❌ **自锁** |

⇒ 差异**只在于名单里多了自己的名字**。这是确定性 bug，不是偶发。

## 二、★ 最值得记的教训：它**看起来完全正常**

bug 从 20:21 存在到 23:5x 才被发现，期间守卫**每 30 分钟认认真真打印一行**：

```
[chainZ3 2026-10-04 22:21:17]   仍在跑（GPU进程=0 名单进程=1 活锁=1 已等 120min）
[chainZ3 2026-10-04 22:51:18]   仍在跑（GPU进程=0 名单进程=0 活锁=1 已等 150min）
[chainZ3 2026-10-04 23:21:19]   仍在跑（GPU进程=0 名单进程=0 活锁=1 已等 180min）
[chainZ3 2026-10-04 23:51:20]   仍在跑（GPU进程=0 名单进程=0 活锁=1 已等 210min）
```

**"日志在持续输出"被误当成"系统健康"。** 它在正常工作啊——只是永远在"忙"。

★ 这是我此前**没有的判据**：一个"等待-然后-动作"的脚本，
**判据本身可能是不可满足的**，而**运行期的日志不会告诉你这件事**。
唯一的办法是**启动时就自证判据可收敛**。

## 三、修复（两处，都已本地验证）

### 3.1 `scripts/chainZ4_shutdown.sh`（新建，替代 chainZ3）

| 修改 | 内容 |
|---|---|
| **① 自锁名** | `SELF_NAME=chainz4`，`LOCK=.../.chainz4.lock` |
| **② 名单排除自己** | `LOCKS="chainaa chainab chainp2 … chaino r448real"` —— **无 chainz4** |
| **③ 双保险** | 主循环两处 `[ "$l" = "$SELF_NAME" ] && continue`（即使将来有人把名字加回去也不会自锁） |
| **④ 启动自检**（新增） | 算一遍判据，若"只有自身锁存活且 GPU 空"就打印 `[自检] ✅ 判据可收敛` |

**本地复现证明**（同一环境：自身锁 + 僵尸锁）：

```
=== 模拟 v3 判据（LOCKS 含自己）===
  ALIVE=1  ⇒ 判「忙」→ 永不关机（就是这次的事故）
=== 模拟 v4 判据（跳过自己）===
  ALIVE=0  ⇒ 判「闲」→ 正常关机 ✅
```

### 3.2 `scripts/clean_locks.sh`（新建，清理失效锁）

同类隐患的通用工具：**"锁文件存在" ≠ "进程活着"**，
残留 PID 若被复用 ⇒ `kill -0` 成功 ⇒ **假性"忙"** ⇒ 同样永不关机。

- 判失效的五条：PID 不存在 / 为空 / 非数字 / `ps` 取不到 cmd / **cmd 里不含链名**
- **默认 dry-run**，`--apply` 才真删
- `--live "chainaa r448real"` 保护在跑的链（**绝不碰**）

**已演练**（构造 4 种锁）：

```
[失效] .chainaa.lock   pid=999999 ⇒ 进程不存在（残留）⇒ 删除
[失效] .chainbad.lock  pid=1      ⇒ 进程不存在（残留）⇒ 删除
[失效] .chainempty.lock pid=''    ⇒ 空或非数字 ⇒ 删除
[保护] .chainz4.lock   pid=602    ⇒ 在跑名单内，绝不碰
汇总：存活 0 ｜ 失效(拟删) 3 ｜ 保护跳过 1
```

`--apply` 后确认：目录里**只剩 `.chainz4.lock`** ✅

## 五、新增铁律 77 / 78 / 79（现 1–79 连续）

| # | 一句 |
|---|---|
| **77** | **守卫脚本绝不能把自己的锁算进"忙"的判据**（自指条件 ⇒ "忙"永远成立 ⇒ 判据必须能收敛到"闲"） |
| **78** | **"锁文件存在" ≠ "进程活着"**；判活必须核对进程身份，防 PID 复用造成假性"忙" |
| **79** | **"看着没问题"不是判据**；"等待-然后-动作"的脚本**必须在启动时自证判据可满足** |

★ 77/78/79 是**同一族**：**判据的"可满足性"与"身份正确性"必须显式验证**，
不能靠"跑起来看着正常"。这与此前的**铁律 6b**（锁与判据须覆盖整条链）是一体两面：
6b 说的是"**别漏**"，77 说的是"**别自指**"。
